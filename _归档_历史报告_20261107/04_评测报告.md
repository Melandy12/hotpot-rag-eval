# 火锅底料风味稳定性智能体 · 知识库检索评测报告（第 1 轮）

- 数据集：`10.24数据整理(1).xlsx`（火锅底料知识文档索引 50 条 / 历史异常案例 50 条 / 时间序列检测数据 30 行）
- 知识库规模：**106 个 chunk**（50 篇文献摘要 + 50 条异常案例 + 6 个批次时序卡片）
- 固定问题集：**15 个意图 × 2 种问法 = 30 道题**（术语版 vs 车间口语版）
- 检索方式：纯 BM25（无嵌入模型），三组对照
- 评测日期：2026-11-06

---

## 一、先给结论

| 结论 | 证据 |
|---|---|
| **BM25 对专业术语问法是够用的，不需要嵌入模型** | 术语版 Hit@1 = **100%**（15/15 全部首位命中） |
| **BM25 对口语化问法是直接失效的，不是"排得靠后"，是"根本召不回来"** | 口语版 Hit@5 仅 **40%**，15 题中 **9 题完全零召回**（返回空结果） |
| **加领域分词词典对口语问法零改善，对术语问法反而造成 1 题退化** | A→B 口语版指标一字未变（26.7% / 40.0%）；术语版 Hit@1 100%→93.3%（"风味稳定性"从第 1 掉到第 2） |
| **加一张人工维护的"口语↔指标"同义词表，口语版从 26.7% 拉到 86.7%** | MRR 0.313 → 0.922，零召回 9 → 0 |
| **但同义词表会污染含口语词的术语题** | "料渣水分"术语版从第 1 位掉到第 2 位 |

**一句话**：你原计划的"先不配嵌入模型"这一步是对的，而且比预想的更成立——专有名词是 BM25 的主场。真正的瓶颈不是"检索算法不行"，是**车间口语和标准指标之间没有一张桥**。这张桥用同义词表补，成本几乎为零、效果可解释；嵌入模型不是第一优先级。

## 三、你点名的四个专有名词，单独拆开看

| 术语 | 术语版命中（原始 BM25） | 口语版（原始 BM25） | 口语版（同义词扩展后） |
|---|---|---|---|
| **酸价** | 首位 DOC-005 ✅ | 首位 CASE-2026-001 ✅ | 首位 DOC-005 ✅ |
| **料渣水分** | 首位 CASE-2026-013 ✅ | **零召回** ❌ | 首位 CASE-2026-013 ✅ |
| **黑水** | 首位 CASE-2026-009 ✅ | **零召回** ❌ | 首位 CASE-2026-009 ✅ |
| **风味稳定性** | 首位 DOC-013 ✅ | 首位是 CASE-2026-019（不在相关集合），第 2 位 CASE-2026-004 ✅ | 第 2 位 DOC-013 ✅ |

> 注：上表"术语版"取 A 组（纯 BM25）。C 组扩展后"料渣水分"从第 1 位退到第 2 位（首位变成 CASE-2026-035），这就是扩展的代价，见第四节。

### 为什么"料渣水分""黑水"会零召回

这是本次最重要的诊断。**两题的病根是同一个：口语提问里根本没有出现语料中的任何一个规范词项，两者词表交集为空。**

**1）"料渣水分"**
口语版原文是"料渣太湿了 炒不干 后面容易坏"——里面**没有"水分"这两个字**，只有"湿""炒不干""容易坏"。而语料里写的是"水分含量""水分活度""脱水"。BM25 是词项匹配，交集为空就是零分、返回空列表，跟排序好坏无关。
术语版原文是"炒制后料渣水分含量 水分活度 控制范围"——"水分""活度"都在语料里，所以首位就命中。

**2）"黑水"**
知识库里描述同一现象的规范表述是"汤色发黑""颜色发黑""色差 L* 值下降""黑色碎屑"，**没有任何一个 chunk 出现过"黑水"**。口语版"黑水是咋回事 煮出来汤是黑的"能匹配的只有单字"黑""汤"，而单字被停用/过滤掉了，于是同样零召回。

**3）反证：加领域词典（B 组）对这两题毫无改善**（26.7%/40% 一字未变）。
这一条很关键——它证明**瓶颈不是分词切得对不对，而是词项压根不存在**。所以"调分词""加词典"这一类动作在这个问题上全是白做。

这两个词恰好代表了你项目最真实的使用场景：**用的人不是说文献语言的人，是车间和客户。**

## 四、同义词表为什么有效，以及它的代价

### 有效的原因
我用了一张 30 条的手工映射表（`03_同义词扩展词典.json`），把口语词映射到**语料中真实存在的规范词**：

```
料渣 → 水分 / 炒制 / 脱水 / 水分活度
黑水 → 汤色 / 发黑 / 色差 / 黑色碎屑 / 色素
哈喇味 → 酸价 / 过氧化值 / 油脂氧化 / 酸败
沫子 → 起泡 / 表面张力 / 乳化剂
鼓起来 → 胀袋 / 产气菌 / 菌落总数
```

本质是**补齐词表**，不是改算法。它之所以有效，是因为你这个领域是**封闭域**——车间里描述异常的说法是有限、可穷举的（50 条异常案例里几乎全是大白话：哈喇味、鼓包、起沫发黑、底下沉一层、沙粒感、肥皂味……）。

### 代价（必须写进方案里）

术语版的退化只有 2 题，但**两题的病因不同，别混在一起归因**：

| 退化的题 | 哪一组开始退化 | 病因 |
|---|---|---|
| 风味稳定性 | **B 组**（加领域词典就退化） | 把"挥发性风味物质"收成一个整词后，它与 DOC-013（PCA 风味评价模型）的部分匹配面被切断，首位让给了 DOC-042 |
| 料渣水分 | **C 组**（同义词扩展才退化） | 术语题里也混着口语词"料渣"，被扩展后追加了"水分/炒制/脱水/水分活度"4 个高频词，把首位从 CASE-2026-013 稀释成 CASE-2026-035 |

注意 B 组这一条：**它说明"加领域词典"不是一个免费的优化**。词典能防止专业词被切碎，但也可能把本该松散匹配的长词绑死。这一条要单独验证，不能跟着同义词扩展一起上。

**修正方向（下一轮要做的）**：
1. **分路判定**：query 先过一遍口语词表，命中口语词才扩展；纯术语题走原路不扩展。
2. **扩展词降权**：扩展词以 0.5 倍权重计分，原始 query 词保持 1.0。
3. **形态控制**：同义词表只映射"现象 → 指标名"，不映射"指标名 → 更多指标名"，避免自我稀释。
4. **词典白名单化**：只把语料里确实存在、且切碎了会丢语义的词加进 jieba 词典，不批量塞；每加一批就在这 30 题上回测。

## 五、口径说明（关系到这组数字能不能直接用）

1. **gold 是"相关文档集合"，不是"唯一标准答案"。** 每题标了 2~8 篇相关 chunk，Hit@k = top-k 里是否出现集合内任一篇。所以 Hit@1 100% 的意思是"首位落在相关集合里"，不是"首位就是唯一正解"。
2. **语料是摘要，不是全文。** 50 篇文献每条只有一行"核心提取内容"。真实全文库体量大一个数量级，BM25 的 IDF 分布会变、竞争文档会变多，**命中率会下降**。这组数字要理解成"上限友好"的基线，导入全文后必须重跑。
3. **知识库只有 106 个 chunk，规模偏小。** 小库下 BM25 的区分度天然偏高，扩到 500+ chunk 后需要在同一问题集上重测。
4. **同义词表是我基于 106 个 chunk 的内容反向整理的**，不是从你们的车间语料里采集的。**下一轮必须换成真实问法样本**（工人/客户实际怎么问），否则这张表等于在测"我猜的词对不对"。

## 六、嵌入检索（bge-m3 / nomic-embed-text）这一半的现状

**没有跑成，原因是环境而不是方案**：本机未安装 Ollama，`ollama.com` 下载在这台机器上持续 0 字节（被墙）。我没有用任何估算数字充数——表里所有数字都是 Python 实际跑出来的。

脚本已经写好并可直接接上（`03_run_hybrid_eval.py`），支持两种后端：

```powershell
# 后端 1：本地 Ollama（拉 bge-m3 后一条命令跑完）
ollama pull bge-m3
python "<仓库根>/03_评测/03_run_hybrid_eval.py" --model bge-m3
```

```powershell
# 后端 2：AnythingLLM / Cherry Studio 自带的 OpenAI 兼容接口
python "<仓库根>/03_评测/03_run_hybrid_eval.py" `
  --model bge-m3 --host "http://127.0.0.1:1234/v1" --openai
```

脚本会一次输出三条曲线，方便你直接看出"混合到底救回了什么"：

| 输出列 | 含义 |
|---|---|
| `*_dense` | 纯向量检索（不看关键词） |
| `*_hybridRRF` | BM25 + 向量 RRF 融合（工业界常用，不用调权重） |
| `*_hybridW` | 加权融合 0.4×BM25 + 0.6×向量（可调） |

向量有缓存（`04_结果/_embed_cache.json`），换模型不会重算语料，第二次跑秒出。

**我的判断是：嵌入模型要先看它能不能解决"词表缺口里没被同义词表覆盖的那部分"。** 现在同义词表已经把口语版打到 86.7%，嵌入模型要证明的是剩下 13.3% 和"新人新说法"，而不是重复解决已经解决的部分。所以跑的时候**重点看 hybrid_dense 在"同义词表没覆盖的新说法"上的表现**，别只看总 Hit@3。

## 七、这直接改变了你项目的技术栈优先级

你原来说的路径是：Cherry Studio 检索问答 → AnythingLLM 作数据库 → 自己 SPC 控制图。实测之后建议改成：

| 优先 | 做什么 | 理由 |
|---|---|---|
| 1 | **把同义词/口语映射表当核心资产维护** | 一张 JSON 表换来 Hit@1 26.7%→86.7%，比调模型便宜一个数量级，且每条映射都能对着案例溯源 |
| 2 | **把 50 条历史异常案例当成"口语语料矿"** | 这张表现在就是知识库里价值最高的部分，异常现象列几乎全是大白话，天然是口语→指标的对照样本 |
| 3 | Cherry Studio 不配嵌入，走关键词/BM25 | 专有名词场景 BM25 100% 命中，配嵌入是浪费 |
| 4 | AnythingLLM 配 bge-m3 做混合 | 到"覆盖新说法"这一层才需要 |
| 5 | **SPC 控制图独立走结构化计算，不进向量库** | 酸价/过氧化值的 CPK、判异规则必须由代码算，检索回来的数值不能当计算结果用——这是你项目里最容易做错的一处 |

关于第 5 条多讲一句：`时间序列检测数据` 和 `历史异常案例` 里的"酸价突破 2.5mg/g 上限""CPK 值偏低"这些，**只能作为检索参考资料，不能作为 SPC 判定依据**。控制图要自己读 `时间序列检测数据` 表算 UCL/LCL、画判异规则。知识库负责解释"为什么异常、怎么处理"，不负责算"是否异常"。
